# LinkedIn demo script — 60 to 90 seconds

A screen recording, no face cam needed. Target 75 seconds; it fits in 90 with
natural pacing.

## Before you record

- [ ] `ANTHROPIC_API_KEY` set — otherwise every answer carries a "Demo mode —
      simulated" badge, which is honest but weakens the demo
- [ ] Signed out, cookies cleared — you want a fresh guest session so the
      nudge fires on cue at the second answer
- [ ] For the 1:08 beat, temporarily set `GUEST_NUDGE_AFTER=2` (the default)
      so the nudge lands inside the take
- [ ] Browser at 1440×900, zoom 100%, bookmarks bar hidden
- [ ] Use Chrome or Edge if you want to show the microphone
- [ ] Sound on if you demo voice; otherwise record silent and caption
- [ ] Do a dry run first — you want the *second* take

## Shot list

### 0:00–0:10 — The problem, stated once

> **On screen:** landing page, scroll slowly through the hero.
>
> **Voiceover / caption:**
> "Most people can't write SQL. So most data sits unused. VoiceQuery lets anyone
> ask a question in plain language — and shows its work."

### 0:10–0:20 — One click into the product

> **On screen:** click **Try the demo**. The dashboard loads immediately with
> the sample dataset selected. No sign-up form, no email.
>
> **Caption:** "No sign-up. Sample dataset already loaded."

This is the strongest beat in the whole video — most demos make you register
before you see anything. Let the speed of it land before moving on.

### 0:22–0:42 — The core loop, with the microphone

> **On screen:** click the **Voice** button, say clearly:
>
> > "Which products generated the most revenue?"
>
> Let the transcript appear in the box. **Pause for a beat on the editable
> text** — that is the trust moment. Press **Ask**.
>
> Let the stage list run visibly: Understanding → Generating SQL → Running query
> → Preparing answer. Then the chart, table and answer land.
>
> **Caption:** "Speak it or type it. You can edit the transcript before it runs."

### 0:42–0:55 — Follow-up, showing memory

> **On screen:** type (don't speak — faster):
>
> > "Now show only September"
>
> The chart updates. Point the cursor at the changed numbers.
>
> **Caption:** "It remembers the dataset and the conversation."

### 0:55–1:08 — The part engineers care about

> **On screen:** expand **View generated SQL**. Hold for ~3 seconds so it is
> readable. Then hover the stage timings.
>
> **Caption:** "Every answer shows its SQL and real measured timings. The query
> is parsed against a read-only allowlist and runs in a sandboxed engine with no
> file or network access."

This is the beat that separates this from a hundred other "AI chat" demos. Do
not rush it.

### 1:08–1:18 — Honest about what the demo is

> **On screen:** the sign-up nudge appears after the second answer. Let the
> viewer read it: *"generated by a simple rule — not an AI model"*. Click
> **Cancel** to show the demo keeps working, then scroll up to the earlier
> results.
>
> **Caption:** "The demo is upfront that it isn't AI. Sign up for real
> answers — anonymous sessions never touch a paid model."

The point being made here is a design one: the free tier can't spend the
operator's API budget, and it says so rather than quietly degrading.

### 1:18–1:25 — Close

> **On screen:** back to the chart.
>
> **Caption:** "React, TypeScript, Fastify, Postgres, DuckDB. Code linked below."

## Suggested post copy

> I built VoiceQuery — ask questions about a CSV in plain language or by voice,
> and get a chart, the rows, and the SQL it ran.
>
> The interesting engineering problem wasn't the chat. It was: how do you let a
> language model write SQL against real data without it becoming a
> vulnerability?
>
> Two independent layers. The generated query is parsed into an AST and walked
> against a strict allowlist — a `SELECT` that hides `read_csv_auto('/etc/passwd')`
> in a subquery or a `UNION` arm gets rejected, because keyword filtering alone
> catches none of those. Then, separately, the query engine itself runs
> read-only with filesystem and network access disabled and the configuration
> locked, so even a query that defeated the parser still fails.
>
> Writing the validator taught me something: my first version walked only the
> AST properties I knew about, and a `UNION SELECT ... FROM users` slipped
> straight through in a property I'd never looked at. The fix wasn't to handle
> that one case — it was to reject *any* structure the walker doesn't recognise.
> Fail closed, not open.
>
> Also in there: a transactional credit ledger with idempotency keys so a
> retried request can't double-charge, per-dataset isolated storage, and
> bring-your-own-key so users can pay their own provider.
>
> One product decision I'd defend: you can try it with no sign-up, but
> anonymous sessions are always served by a local stand-in, never a real
> model — and the UI says so on every answer. "Free to try" shouldn't mean
> "free to drain someone's API budget."
>
> Stack: React + TypeScript + Vite + Tailwind, Fastify, Postgres, DuckDB, Claude.

## Recording notes

- **Do not** speed up the analysis stages in post. The point is that the timings
  are real; a sped-up clip implying sub-second AI latency would be a fabricated
  performance claim.
- Leave the "Demo · not signed in" and "simulated" badges visible and say so in
  the caption. Cropping them out would misrepresent a rule-based answer as AI.
- If you want a take with **real** AI answers, sign up inside the recording
  (or start signed in with `ANTHROPIC_API_KEY` set) — the badges disappear on
  their own once a real model is answering.
- Keep the whole take in one browser tab. Cuts between tabs read as edited-away
  failures.
- 1080p, 30fps is plenty. Trim dead air at both ends.
